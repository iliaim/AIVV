# `/aivv-fix`-specific preference bindings

Detail relocated from `skills/aivv-fix/SKILL.md` Step 1.1 "Resolve `/aivv-fix` Preferences". The **shared** resolution mechanism (W9 golden-schema dispatch + precedence + L1-source forced-override) lives in [`.aivv/configuration.md`](../../../.aivv/configuration.md#resolution-algorithm) — the inline Step 1.1 keeps a one-line pointer to it. This reference is the canonical home for the fix-only KEY catalog that remains specific to this workflow when the shared mechanism is documented separately: the `fix_apply_policy` per-category map, the `apply_polish_mode` legacy mapping, the `--apply-all-polish` / `--dangerously-auto-apply` binding rules, and the one-time `auto_apply_v1` notice.

These bindings sit on top of the shared core (CLI > project config > user config > schema defaults, validated against `.aivv/schemas/config.schema.json` regardless of `schema_version`).

**Target used for preference resolution:**
- If the user explicitly supplied `--target=<dir>`, use that directory. An
  automatic review-to-fix handoff retains the original bound policy provenance;
  its generated target argument does not select a different config.
- Else if `--review-id=<id>` succeeded, use validated stored policy provenance when present, otherwise its validated `target_project`. Re-read current policy; never restore serialized approvals.
- Else if file-backed findings already provide file paths, use the [`.aivv/target-resolution.md`](../../../.aivv/target-resolution.md) algorithm's common-ancestor/git/cwd chain with only those file paths.
- Else if all findings are scoped (`scope_ref` only), skip finding-driven detection and use `git_toplevel(cwd)` with cwd fallback.
- Else use `git_toplevel(cwd)` with cwd fallback.

**Resolution algorithm:** reuse the shared resolution algorithm (W9 golden-schema dispatch + precedence + L1-source forced-override) defined in [`.aivv/configuration.md`](../../../.aivv/configuration.md#resolution-algorithm): CLI > project config > user config > schema defaults, validated against `.aivv/schemas/config.schema.json` regardless of `schema_version`. `/aivv-fix`-specific bindings on top of that core: do not route ordinary `/aivv-fix` preference reads through legacy `config.vN.schema.json` files; do not auto-create config files from `/aivv-fix` except for the minimal user-scope `~/.aivv/config.json` creation needed to persist the one-time `auto_apply_v1` notice marker on non-`--dry-run` invocations.

**Malformed / unreadable config handling:** If preferences cannot be read because a config file is malformed, preserve the original file and follow the warning/fall-through behavior of `/aivv` Step 1.5. Never move or rewrite malformed optional config during reads. If the read is impossible because the host cannot access the file, warn and fall through to schema defaults; do not fail the fix workflow solely because an optional preference file is unavailable.

**Binding rules:**
- `--apply-all-polish` sets invocation-local `fix_apply_policy.improvement=auto` and wins over project/user `fix_apply_policy.improvement` and legacy `apply_polish_mode`. L1-source refusal, high-blast-radius/shared-interface pauses, invasive-improvement deferral, and write-intent gates still apply.
- `--dangerously-auto-apply` is invocation-local only and has no schema/config binding. It wins over the W10 decision queue only after explicit confirmation. It bypasses normal prompts for CHALLENGE, L1-source/manual-review refusal, high-blast-radius pause, low-confidence escalation, and the batched decision surface, but it does not bypass invasive-improvement deferral, `--dry-run`, target resolution, write-intent inspectability/freshness, Step 4.5 REVISE/REJECT stale-intent invalidation, unsupported-risky-path rejection, or post-write verification.
- `fix_apply_policy` is the W10 per-category policy map. Known category keys are `code-bug`, `design-flaw`, `process-violation`, `documentation-gap`, `improvement`, and `clarification-needed`; values are `auto`, `ask`, or `skip`. If the key is absent from both user and project config, bind the golden schema default as the runtime default. If the key is present at any scope, resolve it with normal CLI > project > user > schema precedence, filling omitted category entries from the schema object.
- If explicit `fix_apply_policy.improvement` is absent but legacy `apply_polish_mode` is explicit, map the legacy key for Branch F / POLISH application: `always` → `auto`, `ask` → `ask`, `never` → `skip`. If both are explicit, `fix_apply_policy.improvement` wins. If neither is explicit, the schema default supplies `improvement=ask`.
- `--enable-step-57-execution` / `--disable-step-57-execution` override `enable_step_57_execution` for this invocation.
- `outer_loop_*` values are read from resolved config before Step 6.5.
- `post_review_html_viewer` and `post_review_html_open_mode` are read from resolved config before Step 7's optional post-fix HTML viewer hook.

**One-time auto-apply notice (`auto_apply_v1`):** after resolving `fix_apply_policy`, if any category resolved to `auto` from the schema default (that is, no explicit user/project value supplied that category), check user-scope `_walkthrough_hints_shown.auto_apply_v1`. If absent or null, emit exactly one notice before Step 2 triage: `/aivv-fix now auto-applies only high-confidence low-consequence fixes after safety gates clear. Set fix_apply_policy categories to ask to return to prompting.` Then, only when `--dry-run` is NOT set, create `~/.aivv/` if needed, create a minimal `~/.aivv/config.json` if missing (`{"schema_version":6}` plus the marker), and write `_walkthrough_hints_shown.auto_apply_v1` to the current UTC timestamp while preserving existing config content. If the marker write fails, emit a warning and continue; the notice may reappear on the next invocation. Under `--dry-run`, do not write the marker because dry-run remains read-only.
