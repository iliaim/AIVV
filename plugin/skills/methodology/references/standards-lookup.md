### Step 4: Standards lookup

When validating code against standards:

1. **Start with RULES_SUMMARY.md** if it exists (typically ~400 tokens, covers all rules)
2. **Follow links** to full rule files only when you need detailed patterns or examples
3. **NEVER load all rule files at once** — projects with many rules can have 50K+ tokens of standards

Before citing a specific AIVV standards rule ID in a finding, run the local index lookup. Native reviewer prompts receive an absolute `standards-lookup.mjs` path in their runtime-helper pointers; provider-backed prompts receive the same path in the rendered `Runtime Helper Paths` section. Use that injected absolute path rather than assuming the consuming project has an `AIVV_ROOT` environment variable:

```bash
node "<absolute-path-to-standards-lookup.mjs>" --id <RULE-ID>
```

Use the returned title, family, and file path as the first semantic-fit check. If the indexed title does not match the issue you are describing, search by title or family before citing:

```bash
node "<absolute-path-to-standards-lookup.mjs>" --grep-title "name field"
node "<absolute-path-to-standards-lookup.mjs>" --family ui-ux
```

If the prompt does not contain an injected absolute path, resolve `AIVV_ROOT`
through the bundled `.aivv/runtime-root.md` contract before running the helper;
never repeat `node "$AIVV_ROOT/..."` with an uninitialized variable.

Open the returned standards file when the title alone is insufficient. The lookup helper proves that the ID exists and points at the right catalog region; it does not replace source verification for external MDN, W3C, WCAG, RFC, legal, or research claims.

If no formal rules exist, check for:
- `.eslintrc` / `eslint.config.js` — Linting rules
- `tsconfig.json` — TypeScript configuration
- `.prettierrc` — Formatting rules
- `package.json` scripts — Quality gate commands

**How to use the standards:**
- Each rule has a unique ID, severity (CRITICAL/MAJOR/MINOR), authoritative source, and specific "code patterns to flag" list.
- When the diff matches a "code patterns to flag" pattern, emit a finding at the rule's documented severity, citing the rule ID AND the authoritative source URL.
- Do NOT invent rules outside these standards. If a UI concern looks real but no rule covers it, use general code-review judgment but do NOT cite a fabricated rule ID.
- Do NOT attempt to verify rendered-output properties in code review (contrast ratios, focus-ring visibility, animation timing, cross-viewport layout). Those belong to Tier 2 visual verification — emit the advisory block instead.
