## Focus

Apply these review concerns **in addition to** the universal Phase 2 VERIFY rules. The i18n lens extends code review with internationalization concerns code-observable without running the app in multiple locales.

### Translation-function discipline + CLDR pluralization (see `.aivv/standards/i18n/strings.md`)

The 10 I18N-STR-* rules cover user-facing string handling for multi-locale deployments:

- I18N-STR-01 Translation-function discipline (every user-facing string passes through `t(...)` / `i18n(...)` / `gettext(...)` lookup; no hardcoded English)
- I18N-STR-02 CLDR-aware pluralization (use `Intl.PluralRules` + ICU `{count, plural, one {...} other {...}}`; NOT `n === 1 ? "item" : "items"`)
- I18N-STR-03 Runtime `<html lang>` correctness (matches the actively-rendered translation locale; updates on locale switch)
- I18N-STR-04 ICU `select` for grammatical agreement (gender, formality, case)
- I18N-STR-05 No-concatenation discipline (use placeholders; NOT `"Hello, " + name + "!"`)
- I18N-STR-06 CLDR locale fallback chain (`en-CA` → `en` → root; NOT custom regex parsing)
- I18N-STR-07 Locale-aware collation via `Intl.Collator` (German `ä` collates with `a`; NOT raw codepoint sort)
- I18N-STR-08 Accent-insensitive search via `Intl.Collator` `sensitivity: "base"` or `"accent"`
- I18N-STR-09 Missing-translation handling (signal defect; never silent empty string)
- I18N-STR-10 Message-key naming conventions (namespaced semantic identifiers; NOT inline English-as-key)

### Locale-aware Intl.* API discipline (see `.aivv/standards/i18n/formatters.md`)

The 10 I18N-FMT-* rules cover JavaScript Intl.* API usage for date/time/number/currency/relative-time/list/display-names/segmenter/locale:

- I18N-FMT-01 `Intl.DateTimeFormat` for dates (en-US "12/19/2012" vs en-GB "19/12/2012" — never `date.toLocaleDateString()` without explicit locale)
- I18N-FMT-02 `Intl.NumberFormat` for numbers (US `1,234.56` vs DE `1.234,56` vs FR `1 234,56` vs IN `1,23,456` vs AR `١٬٢٣٤٫٥٦`)
- I18N-FMT-03 `Intl.NumberFormat({style:"currency"})` with explicit `currency` code property (locale formats placement: en-US `$1,234.56`, de-DE `1.234,56 €`, fr-FR `1 234,56 €`)
- I18N-FMT-04 `Intl.RelativeTimeFormat` for "3 hours ago" displays
- I18N-FMT-05 `Intl.ListFormat` for prose lists (Oxford-comma vs no-Oxford-comma per locale + per-locale conjunction word)
- I18N-FMT-06 `Intl.DisplayNames` for language/region/script/currency labels ("German"/"Deutsch"/"Allemand")
- I18N-FMT-07 `Intl.Segmenter` for grapheme/word/sentence segmentation (CJK + Thai/Lao/Khmer/Myanmar + emoji-safe iteration; NOT `string.split(" ")` or `string.length`)
- I18N-FMT-08 `Intl.Locale` for canonical BCP 47 manipulation (`.maximize()` / `.minimize()`; NOT substring parsing)
- I18N-FMT-09 UTC storage + IANA timezone display (NEVER `new Date()` arithmetic in local TZ)
- I18N-FMT-10 Locale-detection precedence (user-pref → URL → Accept-Language → navigator.languages → CLDR root)

### RTL safety + bidi text handling (see `.aivv/standards/i18n/rtl-bidi.md`)

The 10 I18N-RTL-* rules cover right-to-left and bidirectional text patterns (Arabic, Hebrew, Persian, Urdu, Pashto, Yiddish, Sindhi, Dhivehi locales):

- I18N-RTL-01 Root `<html dir="rtl">` for RTL locales (8 canonical: ar/he/fa/ur/ps/yi/sd/dv)
- I18N-RTL-02 CSS logical properties (`margin-inline-start` not `margin-left`; auto-mirror)
- I18N-RTL-03 Inline bidi isolation via `<bdi>` or `dir="auto"` for embedded opposite-direction fragments
- I18N-RTL-04 Mirrored icons (`transform: scaleX(-1)` for directional icons via `:dir(rtl)`)
- I18N-RTL-05 Unicode bidi control characters anti-pattern (U+202A..U+202E + U+2066..U+2069; U+202E phishing-vector security framing)
- I18N-RTL-06 Form-control alignment + `dirname` directionality reporting
- I18N-RTL-07 Dir-attribute propagation across SPAs/iframes/shadow-DOM (MutationObserver + postMessage)
- I18N-RTL-08 Prefer HTML `dir` over CSS `direction` property (MDN normative warning)
- I18N-RTL-09 RTL-aware animations + transforms (sign-flip `translateX` via `:dir(rtl)`)
- I18N-RTL-10 Mixed-direction layouts via per-region `dir` (global LTR nav + RTL content via section `dir` overrides)

## Severity anchors

When `severity_model: impact_likelihood` is active, use these anchors for i18n findings after the two-track discriminator: DEFECT-track findings get IMPACT and LIKELIHOOD before mapping to the shared severity table. In legacy mode, treat these anchors as reviewer reasoning guidance, not an override of the configured shared severity model. Do not upgrade severity merely because a finding cites a CLDR/ICU/MDN/W3C rule; user-visible locale harm and reachable exposure control the rating.

### IMPACT: localized user harm if encountered

- CATASTROPHIC: wrong financial, legal, medical, safety, or identity meaning across a supported locale; bidi spoofing or directionality failure that can mislead users into an unsafe action; broad loss/corruption of localized content or locale-specific transactional data.
- SEVERE: primary workflow unusable or materially misleading for a declared locale/market; payment, scheduling, address, authentication, onboarding, or compliance-critical flow broken by translation, plural, formatter, script, RTL, or bidi handling.
- MODERATE: localized task friction, incorrect display, search/sort/truncation, or layout breakage on a secondary path; recoverable missing translation or locale mismatch that affects a bounded user group or non-critical workflow.
- NEGLIGIBLE: developer-only strings, tests, logs, unused locale catalogs, dormant RTL/CJK/script support, or style/convention drift with no current user-visible locale harm.

### LIKELIHOOD: locale exposure and runtime reachability

- CERTAIN: active production locale or declared market hits the path in normal use; runtime formatter/string/render path always executes; root `lang`/`dir` affects every page for a supported locale.
- PROBABLE: common locale variants, user-generated names/text, common dates/numbers/currency, SSR/CSR locale differences, or shared UI components likely expose the issue to supported users.
- POSSIBLE: less common locale, script, RTL/CJK, translation fallback, admin-only flow, import/export path, or multi-step precondition; project signals future or partial support but the path is not always rendered.
- UNLIKELY: internal-only code, tests, build tooling, disabled locale, unused catalog key, unreachable component, or unsupported locale with no declared market and no current user-visible route.

Use declared project context, README/CLAUDE notes, product copy, locale catalogs, routing, and code paths as evidence for locale/market support; do not assume a formal config key for supported locales. `project_context.deployment` still influences exposure: public multi-locale products raise likelihood, while personal/internal tools lower it unless their own users exercise the locale path. English-only declarations reduce translation-string exposure, but they do not automatically drop formatter defects because US/UK formats, currency codes, timezones, and SSR/CSR runtime locales can still affect English users.

Worked examples:

- A hardcoded English heading in a developer-only test fixture: IMPACT is NEGLIGIBLE and LIKELIHOOD is UNLIKELY; do not emit a user-facing i18n defect.
- A public checkout renders `"$" + amount` for EU customers while charging EUR from price data: IMPACT is SEVERE or CATASTROPHIC depending on transaction risk, and LIKELIHOOD is PROBABLE or CERTAIN on the checkout path.
- A physical `margin-left` rule in a component with no declared RTL locale and no reachable RTL route is usually POSSIBLE or UNLIKELY; the same pattern in an Arabic-market app's primary navigation can become SEVERE with CERTAIN exposure.

## Trigger patterns (flag these explicitly)

- Hardcoded English string in JSX/template body: `<span>Welcome!</span>` instead of `<span>{t("welcome")}</span>`
- Plural ternary: `n === 1 ? "item" : "items"` (use CLDR + Intl.PluralRules; doesn't work for Arabic 6 forms, Russian 3 forms, Polish 3 forms)
- String concatenation for sentences: `"Hello, " + name + "!"` (translator can't reorder; Japanese topic-comment is `<name>さん、こんにちは！`)
- Date format hardcode: `${month}/${day}/${year}` (US-only; breaks in en-GB/de/fr/ja/zh)
- Currency-symbol hardcode: `"$" + amount` (breaks for €/¥/₹/£/zł; symbol placement is locale-specific)
- `date.toLocaleDateString()` without explicit locale argument (uses runtime locale; non-deterministic across SSR vs CSR vs server-region)
- `array.sort()` for user-visible alphabetical list (raw codepoint; German `ä` after `z`; Swedish `å` before `o`)
- `placeholder="Email"` as the only label (placeholder discipline interacts with i18n — translator may miss it)
- `<html>` without `lang` attribute (also fires `visual` lens A11Y-001)
- `<input placeholder="MM/DD/YYYY">` format-hint as the only date guidance (locale-specific format-hint anti-pattern)
- Currency-amount-as-number: `<span>{amount}</span>` rendering raw number with locale-naïve thousands separator
- CSS `margin-left: 16px` for spacing that should mirror in RTL (use `margin-inline-start: 16px`)
- CSS `text-align: left` for paragraph text (use `text-align: start` for auto-mirror)
- `<bdi>` or `dir="auto"` missing on user-generated string interpolated into translated message (`t("welcome", { name: user.name })` — name could be Arabic in English-translated message)
- Hardcoded `dir="ltr"` or `dir="rtl"` on `<html>` root when project supports both — should switch via runtime locale
- CSS `transform: translateX(20px)` in animation that should sign-flip for RTL (use `:dir(rtl) { transform: translateX(-20px) }`)

## Source authority

Every i18n rule cites a canonical normative source per the dev.80+ per-rule WebFetch-verification discipline:

- **CLDR** (Unicode Common Locale Data Repository) — canonical for locale data, plural rules, formatter symbols
- **ICU MessageFormat** — canonical for message-formatting syntax (pluralization, gender, ordinal, choice)
- **WCAG 3.1.1 / 3.1.2** — canonical for HTML `lang` attribute discipline
- **MDN Intl API** — canonical for JavaScript `Intl.*` API surface
- **W3C i18n WG** — canonical for HTML `dir` attribute + CSS Logical Properties + bidi-isolation patterns
- **Unicode UAX #9** — canonical for Bidirectional Algorithm

## Graceful degradation

The i18n lens operates on static artifacts only — no live locale-data probe, no runtime locale-switching test, no rendered-output bidi inspection. If the change set contains no user-facing strings AND no Intl.* API usage AND no dir-attribute / logical-CSS touch, return zero i18n findings: "i18n lens: no internationalization-relevant code in review target; no findings applicable."

If the project declares "English-only, no plans for translation" in maintainer guidance or README, treat I18N-STR-* default MAJOR labels as legacy guidance only; under `severity_model: impact_likelihood`, lower LIKELIHOOD or IMPACT when the string does not reach a supported non-English audience. The I18N-FMT-* discipline still applies to date/currency/number rendering even for English-only deployments (US vs UK formatting differs; SSR vs CSR consistency matters).

If the project declares RTL-language target (ar/he/fa/ur/ps/yi/sd/dv market), treat I18N-RTL-* default and escalation labels as legacy guidance only; under `severity_model: impact_likelihood`, declared RTL support raises LIKELIHOOD, and final severity still follows the shared IMPACT x LIKELIHOOD table.

**Out-of-lens:** AIVV's i18n lens does NOT cover translation-quality, locale-specific UX conventions (date format separators, name-ordering conventions, address-field-ordering), or jurisdiction-specific legal language. Those are translator + UX-researcher concerns. AIVV identifies the code-pattern; humans determine the locale-appropriate content.
