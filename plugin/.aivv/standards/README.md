# AIVV Standards

This directory contains reference standards that the AIVV code-reviewer consults when reviewing diffs that touch UI code. These docs are **authoritative baseline standards** — curated from W3C WAI, WebAIM, NN/g, MDN, GOV.UK Design System, and other authoritative sources — not AIVV-invented rules.

## Generated Rule Index

`.aivv/standards/index.json` is generated by the author-side repo tool `tools/standards-index.mjs` (AIVV source repo; not shipped with the plugin).
It maps shipped rule IDs (`A11Y-*`, `AS-*`, `COMP-*`, `CQ-*`, `DP-*`,
`HEU-*`, `I18N-*`, `IS-*`, `MC-*`, `RTV-*`, `UJ-*`, `UX-*`, `VD-*`,
and `VVT-*`) to title, source file, line, and standards family. The generator
indexes `### RULE-ID: title` headings only so family bucket headings such as
`## UJ-AC:` and `## RTV-AXE-*` do not appear as rules. Do not edit the index by
hand; update the source rule heading and run `node tools/standards-index.mjs write` from the AIVV source repo (author-side).

Additional standards files planned for dev.107+ instructs it to **conditionally consult** these standards — not every review needs them. The trigger is:

**If the diff touches any of these file types / path patterns, consult the standards:**
- `**/*.{html,tsx,jsx,vue,svelte}`
- `**/*.{css,scss,sass,less,styl,module.css,module.scss}`
- `**/*.{png,jpg,jpeg,webp,avif,gif,svg,ico}` (asset changes)
- Frontend-package paths (e.g., `app/`, `pages/`, `components/`, `src/ui/`, `src/frontend/`, `web/`, `client/`)
- Viewport/document-level files (`index.html`, `app/layout.*`, `_document.*`, `head.*`)

When triggered, the reviewer:
1. Reads `accessibility.md` and `ui-ux.md` to look up specific rules matching the diff's patterns
2. Emits findings at the rule's documented severity (CRITICAL / MAJOR / MINOR) citing the rule ID and authoritative source
3. Separately checks `visual-verification-triggers.md` to decide whether to emit a `⚠ Visual verification required` advisory block after the findings

The reviewer should **NOT**:
- Try to verify rendered-output properties (color contrast ratios, focus ring visibility, animation timing, layout at different viewports). Those are runtime checks; the reviewer emits the visual-verification advisory so the user runs them externally.
- Invent rules not in these standards. If a diff pattern looks problematic but no rule covers it, the reviewer can still flag it using general code-review judgment but MUST NOT cite one of these rule IDs.
- Re-derive WCAG criteria from first principles. The standards doc curates what matters; trust it.

## Scope boundary

These standards are intentionally **minimum baselines**, not maximums. They exist to prevent common, high-impact defects — not to enforce design-system choices, enforce a specific style guide, or codify team preferences. Project-specific patterns that extend these baselines should live in the project's own `maintainer guidance` or contributor docs, not here.

## Maintenance

These standards are curated content, not author-invented. When adding a rule:

1. **Cite an authoritative source** — W3C WAI, WebAIM, NN/g, MDN, GOV.UK, USWDS, web.dev. No "we think it's good practice" entries.
2. **Verify the rule is code-reviewable** — if verification requires rendered output, put it in the Out-of-code-review-scope section, not the main checklist.
3. **Follow the numbering convention** — `A11Y-NNN`, `UX-NNN`, `VVT-NNN`; sequential per file.
4. **Ship with a positive + negative fixture** if `validate.sh` tests the rule mechanically (currently none do — these are reviewer-reference docs, not lint rules).

## Relationship to Tier 2

These standards are the **Tier 1 static-review layer** for UI/UX/a11y concerns. They do NOT replace optional B3 runtime evidence for `/aivv --lens=visual` (generated probe scaffolds plus user-run Playwright JSON ingest by default; host browser adapters only when explicitly available). The separation:

- **Tier 1 (here, now)**: catches patterns in source code. Reviewer consults these docs during every UI-touching diff. No MCP dependency. Ships in v0.1.
- **Runtime evidence (optional)**: verifies rendered app behavior through supplied artifacts. Catches pixel-diff regressions, computed contrast, focus-ring visibility, animation jank. B3 default path is generated Playwright probes plus user-run JSON ingest; Playwright/DevTools MCPs are optional host adapters.

Runtime evidence uses these standards as the documented contract for what rendered-output verification enforces — same content, different evidence model.

## Self-contained principle

Per AIVV's self-contained principle: these standards live inline in the plugin. AIVV does NOT reference external plugins (e.g., `agent-skills:ui-ux-standards`) as required dependencies. If an external skill provides useful additional content, the user can optionally consult it — but AIVV's baseline checks are fully functional without it.
